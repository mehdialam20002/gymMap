# KNOWN LIMITATIONS

> **What this file is.** The complete, numbered register of every place where this platform will
> deliberately do **less** than the source document asked for, or less than a reasonable reader of
> `MASTER_PRD.md` might assume. It exists because `PHASES.md` Cross-Phase Rule 3 forbids silent
> loss: *"If a source requirement cannot be honoured, it is recorded in `KNOWN_LIMITATIONS.md` with
> a reason — never silently dropped."*
>
> **Scope.** Phase 1 of the Gym Marketplace & Multi-Tenant Gym Management SaaS, baselined against
> `MASTER_PRD.md` v2.0 (04 Aug 2026). Identifiers in the *Related PRD id* column are the stable
> identifiers defined in the PRD's *Identifier conventions* table and must be used verbatim in
> tickets, commits and tests.

## ⚠️ UPDATE TRIGGER

**This file is edited whenever a deliberate gap opens between what was asked for and what will be
built.** Concretely, an entry is added, amended or closed the moment any one of the following
happens — in the same change that causes it, never afterwards:

| # | Trigger event | Required action |
| :-: | :--- | :--- |
| 1 | A requirement in `MASTER_PRD.md` is knowingly not going to be delivered in Phase 1 | Add an entry before the decision is considered made |
| 2 | A requirement is delivered in a reduced, narrowed or partial form | Add an entry stating exactly what is and is not delivered |
| 3 | A design decision forecloses a behaviour a reader would reasonably expect | Add an entry under *Design-Imposed Limits* and cross-link the `DECISION_LOG.md` entry |
| 4 | A defect is investigated and the disposition is "accept, do not fix" | Convert the defect to an entry here, citing the C8.5 severity it was triaged at |
| 5 | An `OQ-` open question is answered and the answer removes or narrows scope | Amend the affected `OQ-` entry and any entry that depended on its default |
| 6 | An `ASM-` assumption is falsified, a `CON-` constraint tightens, or a `DEP-` dependency changes availability | Amend the affected entries and re-score their impact |
| 7 | A change request under Part C §C10 is approved that removes scope | Add an entry referencing the change request |
| 8 | A limitation is removed by shipped work | Mark the entry `[CLOSED]` with the date and the delivering milestone — do **not** delete the row |

**Ownership.** The Technical Lead / Architect maintains the register. Entries in the
*Deferred Scope*, *Explicit Non-Goals* and *Deferred Priority* sections may only be added or closed
with the Client Sponsor's agreement, because they are commercial scope, not engineering judgement.

**Review cadence.** Reviewed at every phase gate in `PHASES.md`, at every sprint boundary in Part C
§C9.1, and as a mandatory input to the Part C §C8.4 UAT briefing so that no UAT participant
discovers a deliberate limitation as if it were a bug.

**Identifier rule.** `KL-` identifiers are stable and never reused, matching the PRD's own rule for
requirement identifiers. A withdrawn entry is marked `[WITHDRAWN]` and left in place.

## How to read a limitation

Three different things get confused with one another in projects of this size. They have different
owners, different homes and different correct responses. Classify before you record.

| | **Limitation** | **Defect** | **Tech debt** |
| :--- | :--- | :--- | :--- |
| **What it is** | A deliberate, accepted gap between what was asked for and what will be built | An unintended divergence between what was specified and what exists | A deliberate shortcut in *how* something is built, taken knowingly, that we intend to repay |
| **Was it chosen?** | Yes, and by someone with the authority to choose it | No — nobody chose it | Yes, but the choice is about construction, not about behaviour |
| **Who decides** | Client Sponsor (scope) or Architect (design) | Nobody. It is found, not decided | Engineering, with a recorded payoff trigger |
| **Correct response** | Record here, disclose it to users and UAT, revisit at its trigger | Fix it. Triage per Part C §C8.5 (S1 blocks release, S2 same day, S3 next release, S4 backlog) | Register it in `TECH_DEBT.md` with its interest rate and payoff trigger |
| **Where it lives** | This file | The defect tracker | `/docs/TECH_DEBT.md` |
| **What proves it** | A test that asserts the *absence* of the behaviour on purpose, so the gap cannot close by accident | A regression test that fails before the fix and passes after | An architecture fitness test that stops the shortcut spreading |

**The three-question test.**

1. *Did we mean for the system to behave this way?* — **No** → it is a **defect**. Stop. Fix it.
2. *Is the gap in what the system does, or in how it is built?* — **What it does** → **limitation**,
   record here. **How it is built** → **tech debt**, record in `TECH_DEBT.md`.
3. *Can I name the condition under which we would revisit it?* — **No** → the entry is not finished.
   A limitation without a revisit trigger is an excuse.

### What does **not** belong in this register

- **Anything that is simply not yet built but is in Phase 1 scope.** That is a sprint backlog item
  (Part C §C9.1), not a limitation.
- **Anything on the Phase 2 roadmap that Phase 1 was never asked to deliver and that no PRD
  identifier claims.** Part A §A11 is the roadmap; only the §A4.2 `W` items and the `C`-priority
  requirements are limitations, because those were written into the PRD and then held back.
- **Defects currently open against derived documents.** For the record, three are open right now and
  they are **defects, not limitations** — they must be corrected, not accepted:
  1. `PHASES.md` Phase-G acceptance gate still asks `Why Express?`. That is residue from the draft
     superseded by the 2026-08-06 stack ruling. The PRD's Baseline Decisions table and Part C §C1.1
     select **NestJS 10 on Node.js 20**. The line must read `Why NestJS?`.
  2. `PHASES.md` Phase-4 acceptance gate asserts *"Zero Prisma schema or migration files written
     yet"*, and Phase-6 asserts *"Component inventory maps to shadcn/ui primitives"*. Both name
     additions that are still `PROPOSED` in `STACK_ADDITIONS.md` (A-01, A-04) and neither may be
     presupposed by a gate.
  3. `PHASES.md` Phase-2 acceptance gate requires `BusinessRules.md` to cover *"all 78 `BR-`
     rules"*; the enumerated catalogue contains 95 identifiers (see **KL-004**).

**each carries rework exposure if the client later answers differently**. This is a limitation, not
merely a risk, because the gap between "what the client will eventually want" and "what we will
build" is deliberate and accepted: we are choosing to build rather than to wait.

`BLK-02` in `PHASES.md` tracks the open questions as a programme blocker. Every default applied must
be recorded in `DECISION_LOG.md` at the moment it is applied, with a pointer back to the `OQ-` id.

## Register hygiene

| Rule | Detail |
| :--- | :--- |
| **Identifiers are permanent** | A `KL-` id is never reused. A limitation that no longer applies is marked `[CLOSED <date> — <milestone>]` in the *Limitation* cell and kept in place, exactly as the PRD keeps `[WITHDRAWN]` requirements for traceability |
| **Every entry has a revisit trigger** | An entry whose *Revisit trigger* cell says only that it is permanent must say **why** it is permanent and which rule makes it so. An entry with no condition and no permanence rationale is incomplete and blocks the phase gate |
| **Every entry cites a real identifier** | The *Related PRD id* column carries `OBJ-` `KPI-` `BR-` `FR-` `NFR-` `US-` `AC-` `SCR-` `API-` `RSK-` `OQ-` `ASM-` `CON-` `DEP-` `BAC-` `E2E-` `UAT-` identifiers or a named PRD section. Prose references are not acceptable |
| **Deliberate absences are tested** | Where a limitation is a foreclosed behaviour (`DESIGN-LIMIT`), the absence is asserted by a test so it cannot close by accident. `AC-REV-01.2` is the model: *"when I look for a delete or edit action on it, then none exists anywhere in the interface or API"* |
| **UAT is briefed from this file** | Every `DESIGN-LIMIT`, `NON-GOAL` and `DEFERRED-PRIORITY` entry that a UAT persona can encounter is listed in the Part C §C8.4 script briefing, so a participant never raises a deliberate limitation as a defect |
